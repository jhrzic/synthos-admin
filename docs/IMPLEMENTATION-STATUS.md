# SynthOS Admin — Implementation Status

Engineering continuity reference. Not marketing copy. `REAL` means backed by a real database
write/read, a real cryptographic check, or a real network call whose failure is honestly
reported — never a claim resting on UI presence alone. As of "Platform Completion Pass VIII"
(Launch Hardening / Security Closeout — see `docs/adr-007-launch-security-boundaries.md`), on top
of Pass VII (Runtime Activation / Deployment Readiness — `docs/PRODUCTION-READINESS.md` and
`docs/OPERATOR-RUNBOOK.md`), `REAL` for anything runtime-dependent additionally means
**runtime-proven where a runtime is required** — code existing and being wired is not enough on its
own; see each row's own evidence. Builds on Pass VI (Windmill external execution control plane —
`docs/adr-006-windmill-external-execution-control-plane.md`), Pass V (Skills Execution Engine + real
MCP Connectivity + Runtime Observability + Provider Capability Matrix + Apollo/Guardian fabrication
fixes), Pass IV (Master Admin User Management + Second-User Onboarding + Workspace Membership
Management + Workspace Switcher + Admin Audit Trail) and Pass III (Identity + Authorization +
Workspace Authority + Master Admin + MCP + Hermes Phase 2 re-verification).

**Pass VIII in one paragraph:** closed the three named launch-security blockers with real, tested
code — rate limiting (`lib/rate-limit.ts`, tiered, process-local), `/api/terminal/exec` demoted from
a generic production shell to structurally `DEV_ONLY`, and reverse-proxy/TLS readiness (trust-proxy
config, security headers including a real CSP, a Caddy example). Found and fixed two real bugs its
own work introduced (a WAL-mode backup correctness gap, a concurrent-restore race) via a genuine
content-level restore drill, plus a pre-existing millisecond-tie ordering race in two "most recent
row" queries. Bounded MCP response size (previously unbounded). Reduced the main JS chunk ~20% via
targeted lazy-loading, verified live in a real browser. **That same browser walkthrough found the
application's default landing screen shows fabricated demo data** (unrelated to any of this
project's real backend work) — see `docs/DEMO-PROFILE.md` and the Master Admin row below.

**This deployment currently has zero external credentials configured** (no `.env` file, no
exported shell variables, verified directly in Pass VII) — every subsystem below that needs a real
external connection is honestly `NOT_CONFIGURED`, not because the code is missing but because
nothing has been provisioned in this environment yet. Core platform startup (auth, database, Vault,
memory index, receipt signing) requires none of them and was proven live: server started with a
completely empty environment, reached `/api/ready` → `200 {"ready":true}`, and survived a full
process restart with identical user/session data (see `docs/PRODUCTION-READINESS.md`).

Legend: **REAL** — real backing, evidenced. **PARTIAL** — some real paths, some gaps or
unverified pieces. **NOT_IMPLEMENTED** — honestly absent, no fabricated stand-in. **DEFERRED** —
explicitly out of scope by a settled decision (ADR or project instruction), not a gap to close
opportunistically.

## Cross-cutting notes

- **Runtime and provider architecture boundaries** (Hermes MODEL vs Hermes RUNTIME, the skill
  executor's four target types, the MCP connectivity boundary, why skill execution deliberately
  does not join the task/artifact/Aegis/receipt spine, and the status-truth contract) are
  documented in full in `docs/adr-005-runtime-provider-boundaries.md`.
- **Second-user onboarding and the last-active-admin invariant** are documented in full in
  `docs/adr-004-user-onboarding-lifecycle.md` — read that for the `setup_required` account
  lifecycle state, the one-time setup-token model, and why `setPlatformRole`/`setUserStatus`
  refuse an operation that would leave zero active `platform_admin` accounts.
- **Identity and authorization architecture** is documented in full in
  `docs/adr-003-identity-workspace-authority.md` — read that for the session model, the
  platform-vs-workspace authority split, the public-route allowlist, the internal-service-token
  pattern, and CSRF defense-in-depth. `activeWorkspaceId` (client-supplied, in the UI or any
  request body/query) is explicitly documented there as a **requested** workspace, never
  authorization proof — every route independently verifies it against a real membership row.
  Pass IV's workspace switcher (`SidebarNav.tsx`) now sources its options from a real
  `authorizedWorkspaces` prop threaded from `AuthGate.tsx` → `App.tsx` (previously three
  hardcoded fake workspace ids/labels left over from before Pass III); the last-chosen workspace
  is persisted to `localStorage` for UI convenience only and is re-validated against the live
  `authorizedWorkspaces` list on every change, never trusted as authorization.
- **Live-verified, not just unit-tested.** Pass III's authorization wiring was proven against a
  real running server (both via `curl` and a real Chrome browser session): anonymous blocked
  everywhere except the public allowlist, cross-workspace access blocked, workspace-role
  escalation blocked, platform-admin routes correctly gated in both directions, and — the subtle
  case — platform admin does **not** silently bypass ordinary workspace membership checks for
  tenant data it isn't a member of.
- **Workspace isolation** (the pre-existing `resolveWorkspaceId()` scoping) is unchanged and still
  necessary — Pass III adds membership authorization *in front of* it, not instead of it.
- **No new database engine** was introduced. Every table added this pass (`users`,
  `user_sessions`, `workspaces`, `workspace_memberships`) lives in the same SQLite file every
  other table already uses.
- **No new npm dependency** was added in Pass III, IV, or V. Password hashing uses Node's built-in
  `crypto.scrypt`; session-cookie parsing is a ~10-line hand-rolled reader rather than adding
  `cookie-parser`; CSRF defense is an Origin-header check rather than adding `csurf` (unmaintained
  upstream); MCP connectivity (Pass V) is a plain `fetch`-based JSON-RPC client rather than an
  MCP SDK dependency (none is installed, none was added), and credential encryption uses Node's
  built-in `crypto.createCipheriv('aes-256-gcm', ...)` rather than a KMS/vault library. `tar@^7`
  (added in Pass II, for `lib/backup.ts`) remains the only third-party dependency introduced
  across all five platform-completion passes.
